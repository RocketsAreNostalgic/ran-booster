Findings recorded while building the inventory (code facts):

1. **Only one native list-table exists** (surface 1). Surfaces 4, 5 use DT with the same visual
   table language but their own CSS twice over: `30-provider-cards.css:316-345` and `:823-897`
   describe the same columns, and the mobile stacking rules exist in both
   `80-responsive.css:31-94` (`provider-management-table`) and `:412-446` (`credential-table`).
2. **Activity's ARIA is invalid.** `role=table` contains `ul > li`, which are list roles, so the
   `role=row` descendants are not owned by the table in the accessibility tree (verify in browser
   with the a11y tree). The sibling surfaces use real `<table>` or consistent `role=list`.
3. **No table has `aria-sort`; the package, provider and repository-detail tables have no
   caption.** The diagnostics and Transporter tables do.
4. `ProviderManagementTableRenderer` pagination uses an inline `onchange` auto-submit with no
   no-JS submit button (violates the native-fallback expectation).
5. Dead CSS: `80-responsive.css:235-238` targets `td.ran-booster-package-row__content` and
   `__secondary`, which no markup emits (the view uses `__identity`, `__summary`, `__actions`).
6. The package page has **three different control rows** in one Card: filter row + search
   (`package-list-controls`), then bulk row (`tablenav`), then the table. The search box
   forces 40px controls (`60-packages.css` search rules) while sibling selects/buttons keep WP's
   30-32px (verify in browser; likely a visible height mismatch in the same row).
7. Activity and Managed Plugins/Themes share `ran-booster-package-list-controls` /
   `-filters` classes, so a change to the shared toolbar CSS moves both (good for consistency,
   but one slice must own both).
8. Package table mobile behaviour relies on core `wp-list-table.plugins` responsive stacking,
   which is the reason the `rowspan` workaround rules exist (dead selector above).
9. HTMX interactions: row mutations use `hx-select=#wpbody-content` `outerHTML` swaps of the
   whole content region (`assets/ran-booster-packages.js:498-502`), so selection is naturally
   reset (no stale selection). Per-row progress badges update by fragment through
   `data-ran-booster-package-progress`. Any restructuring must keep those hooks:
   `data-ran-booster-bulk-form`, `-select-all`, `-selection-status`, `-bulk-apply`,
   `data-ran-booster-package-progress`, `data-ran-booster-activity-*`.

### 1.3 Recommended design direction (needs owner sign-off on the starred items)

- Frame: one Card per collection, toolbar and table inside it with the Card's 24px inset on the
  toolbar and a flush table (already how `ran-booster-package-collection` works,
  `60-packages.css:619-646`). Do not add insets to cells.
- Table density: desktop rows keep WP's table density (cell padding `--ran-booster-table-cell-padding`
  8/12). Explicitly **do not** apply the 44px touch-row size to desktop; keep 44px only at
  max-width 782px (the repository record action group forces `min-block-size: 44px` at all
  widths, `40-tables-and-pills.css` `.ran-booster-repository-record__action-group`, which is
  the exact misuse the issue warns about).
- Single toolbar row: [filters][search] on one line, bulk actions + selection status +
  item count on the second line using `tablenav` (surface 1), identical order on surfaces 2, 4, 5.
- Scan hierarchy for surface 1: line 1 name (700, 14px), line 2 repo (12px muted), then the two
  state lines; Management column carries one prominent badge plus the status line; keep the
  actions column right-aligned and cap it at two visible controls (see star 1).
- Missing states: add a **loading** treatment for load-older (exists), skeleton is not needed
  for server renders; make "unknown/partial" distinct from "none" (already true for surface 1's
  copy; ensure the item count never reads `0 items` when `$package_list_unavailable`).
- \* **Owner decision 1:** row actions. Today every row shows Reinstall (primary) + Edit settings
  (+ add-on actions); five primary buttons per page compete. Options: (a) keep, tighten gap and
  align button heights; (b) Reinstall to secondary button, Edit settings as primary-link; (c)
  overflow Menu (needs component runtime). Recommend (a) now, (c) as a later slice.
- \* **Owner decision 2:** whether the packages table gains sorting and pagination (neither
  exists; sort needs a presenter change and server query; affects #613/#614/#616 scope, so
  coordinate). Recommend no for beta.44 unless inventories are known to be large.

### 3.2 Options

**Option 1: Spacing and hierarchy only (smallest).** Separate the link choice as its own block
and style it as a checkbox row, not as a field.

```php
<div class="ran-booster-package-link-choice"> <!-- inside [data-ran-booster-branch-install-actions], above the button group -->
  <label class="ran-booster-package-link-choice__label">
    <input type="checkbox" name="ran_booster[dry-run]" ...> Link installed plugin
  </label>
  <p class="description">Let Booster manage an already installed plugin instead of deploying it now.
    The installed folder name must match the repository package name.</p>
</div>
```
```css
.ran-booster-package-link-choice { margin-block-start: var(--ran-booster-space-20); padding-block-start: var(--ran-booster-space-20); border-block-start: 1px solid var(--ran-booster-border); }
.ran-booster-package-link-choice__label { font-weight: 400; }  /* body weight, not a field title */
.ran-booster-package-link-choice .description { margin-inline-start: 1.75rem; font-size: var(--ran-booster-font-size-sm); }
```
Pros: no DOM-order change (the section-order test stays), no behaviour change, no new copy; keeps
the checkbox under Updates but now clearly a separate decision. Cons: still a checkbox that
silently changes the primary button meaning.

**Option 2: Move the choice next to the action (grouped as "how to add").** Put the checkbox
immediately above the button group and put the two description lines inside the same block,
with the divider between the Updates field and this block; add `aria-describedby` from the primary
button to the description. Optionally let the primary label follow the state in JS
("Install plugin" / "Link plugin") only if the owner approves the label.

```css
.ran-booster-settings-actions { margin-block-start: var(--ran-booster-space-12); }  /* checkbox block above owns the divider */
```
Pros: the control that changes the button sits directly above it; clear causal chain
(Updates, then Link yes/no, then submit). Cons: label change is a JS edit in
`ran-booster-packages.js` plus new msgids; "Install and add another" label also becomes
questionable in link mode; owner review required (issue says label changes must follow verified
behaviour and owner review).

**Option 3: Radio/segmented choice "Install new" vs "Link installed" (replace the checkbox).**
Two options in a fieldset with legend "Package source on this site"; primary button label comes
from the selection. Uses the public `@wordpress/ui` radio group control if ever mounted, otherwise
native radios styled like the Update-source choices already on this page
(`source-choices.php`, existing `aria-pressed` choice buttons).

Pros: the two outcomes become explicit and equal; the question is answered before the button.
Cons: highest churn: form field changes from checkbox `dry-run` to a radio (server contract
`PackageOperation` reads `isset($input['dry-run'])`, so the radio would need to still emit
`dry-run`), changes tests and doc references, and the issue says explicitly not to treat a control
replacement as approved. Not recommended for beta.44.

| | 1 spacing/hierarchy | 2 move + describe | 3 radio choice |
|---|---|---|---|
| Fixes "tacked on" | mostly | yes | yes |
| Behaviour/contract change | none | none (label optional) | high |
| Copy change | none | optional label only | new strings |
| Test churn | CSS pins only | `RepeatPackageViewTest` order maybe, JS test if label | high |
| Theme parity | automatic (shared) | automatic | automatic |
| Fits "smallest coherent design" | best | good | no |

Recommendation: **Option 1 now; Option 2's `aria-describedby` and block adjacency as the follow-up;
defer any label change and Option 3.** Merge the two descriptions into the checkbox's single help
block only if the owner accepts compressing copy (the issue says do not invent or shorten wording
without review; keeping both paragraphs is the conservative choice). Keep the checkbox DOM order
after the Updates select so `RepeatPackageViewTest` keeps passing.
