## #748 Readiness step blocks (implemented)

Commit `be9c7703`. Files: `assets/ran-booster-repository-webhook-management.css`, `tests/Admin/AdminAssetContractTest.php`.

Shared renderer: one `<ol class="ran-booster-webhook-steps ...">` with `li.ran-booster-webhook-step` children (marker span, `strong`, `p`), emitted by `RepositoryWebhookManagementControls::render_repository_webhook_lifecycle` (4 steps, Push-to-deploy / Branch) and `ReleaseWorkflowDisplay::repository_lifecycle` (3 steps, Releases). Both share one stylesheet, so one fix covers GitHub, Bitbucket and other providers.

Causes found:

1. Fixed `repeat(4, minmax(0,1fr))` / `repeat(3, ...)` and a viewport-only 782px breakpoint. Inside the WP admin menu plus Card gutters plus the 290px sidebar the main column is far narrower than the viewport, so four columns were about 120px each, hence the "Site recei ver" fragments.
2. Uneven heading-to-description gap: each `li` is a 2-column, auto-row grid and grid items stretch to the tallest neighbour, so the spare height was distributed across the two auto rows. A short `li` beside a tall one got a large blank band between heading and description.

Changes:

- `.ran-booster-webhook-steps` is now `repeat(auto-fit, minmax(min(100%, var(--ran-booster-step-min-inline-size)), 1fr))` with a local `--ran-booster-step-min-inline-size: 208px`. It sizes from the list's own usable width (no viewport assumption), so it reflows 4 to 3 to 2 to 1 as the content box shrinks, never producing a column under 208px. Ordinary words are no longer broken. The `min(100%, ...)` keeps one column valid when the container is under 208px.
- Removed the release-specific `repeat(3)` override and the 782px `grid-template-columns: 1fr` override (both superseded).
- `.ran-booster-webhook-step` gains `grid-template-rows: auto 1fr; align-content: start`, so the description sits at a constant 4px (the existing `p` margin) under its heading in every step and spare height lands below the text. `strong` gets `overflow-wrap: break-word` so only an unbreakable long token wraps, never ordinary words.
- Markup unchanged (no PHP changes); order, numbering, aria-label, state classes untouched.
- Guard test updated in `AdminAssetContractTest` (auto-fit rule, token, no fixed `repeat(3|4)`, no release override, no 782px override, row packing).

Known trade-offs for the owner:

- Four steps with a 208px minimum can show 3+1 in the 700-930px content-width band. Alternatives: raise the minimum so it jumps 4 to 2 (2+2) or accept 3+1. This is a taste call.
- Heading wrap differences between neighbouring steps still shift the description start by one line, because each step is its own grid. Aligning descriptions across steps needs `grid-template-rows: subgrid` on the list. I did not do it, since I could not see the result and gap handling in subgrid is subtle; it is a clean follow-up if wanted.
- I did not use container queries: the codebase only uses them in onboarding, and auto-fit already tracks the element's own width.

EYEBALL THIS: Repositories, a repository, Branch tab and Releases tab (and a Bitbucket repository if available) at 1440, 1100, 900, 782 and 390px, plus 200% browser zoom. Check no fragmented words, equal heading-to-description gap in every step including a wrapped heading, no orphaned oversized blank space, release publishing's 3 steps reflowing 3 to 2 to 1.

## #747 Secondary links below repository status Cards (assessment only)

Current state:

- "Review shared owner secret" (or "Review repository secret"): built in `RAN/Admin/ProviderRepositoryRowsNormalizer.php:441-454` as the single entry of `status_links`, only when coverage is `repository` or `shared` and there is no "Add repository secret" action. Rendered by `RepositoryDetailRenderer::render_status_links` (lines 497-520) as a bare `<p class="ran-booster-repository-detail__status-links">` under the Integration status Card in the main column (line 77). That class has no CSS. It is a Secrets-view link, destination and scope unchanged.
- "View repository activity": `RepositoryDetailRenderer::render_activity` (line 332), the last paragraph inside the Management history Card body in the `aside` sidebar. Always present.
- Layout: `.ran-booster-repository-detail__layout` is a 2-column grid (1.5fr / 250-290px), sidebar sticky; it stacks under 960px, putting the sidebar link far below the main link.

Why they feel disconnected: one is an orphan paragraph outside any Card, the other sits inside a different Card in a different column; both are plain links with different surroundings, and they have no shared parent or row.

Options:

A. Shared link row under the grid (the owner's bar idea, kept as links).
```
+------------------------+ +----------------+
| Integration status     | | Management     |
|                        | | history        |
+------------------------+ +----------------+
Review shared owner secret  ·  View repository activity
```
One `nav`/`p` below `.ran-booster-repository-detail__layout`, outside both columns (render in the `status` branch after line 98). Pros: one place, one code path, reading order after both Cards; narrow stack is naturally last. Cons: far from the Integration Card it relates to; the secret link is conditional, so the row is sometimes one link; needs the 24px card gap above and tokens, and must stay link-styled (#735), not buttons.

B. Move each link into the footer of the Card it belongs to.
```
| Integration status ...      |   | Management history ... |
| ----------------------------|   | ---------------------- |
| Review shared owner secret  |   | View repository activity|
```
Use the Card's own footer/body-end treatment for both (the activity link is already in its Card body; add the secret link as the Integration Card's last row). Pros: smallest change, links stay beside the facts they act on, no orphan outside a Card, no new group. Cons: still two places, but now symmetric (both at the bottom-left of a Card) which fixes the visual disconnect; requires the Integration status Card content to accept a trailing row (it is rendered by `render_status`, line 136).

C. Single "Related" list in the sidebar.
```
Management history Card
Related
- Review shared owner secret
- View repository activity
```
Pros: one list, both rows in one column, sticky. Cons: moves the secret link away from the status it concerns, and on narrow screens both sit at the very bottom; the sidebar is history, not navigation, so a "Related" group needs new heading copy (violates minimal copy).

Recommendation: B (smallest, consistent, no new components or copy, preserves conditional behaviour: the secret link simply keeps its existing `status_links` condition and renders inside the Card). If the owner prefers a single place, A with link styling. Do not use button styling and do not add an external-link arrow (internal destinations).

Shared ownership: `RepositoryDetailRenderer` (render_status_links, render_activity), data from `ProviderRepositoryRowsNormalizer::status_links`; all providers use the same renderer. Keep the `status_links` conditional unchanged to avoid manufacturing a secret destination, and add a CSS rule for the currently unstyled `.ran-booster-repository-detail__status-links`. Needs the owner's decision: A vs B vs C.

## #754 Transporter contrast and hierarchy (assessment only)

### Method

Values read from the source: Booster tokens in `assets/ran-booster/00-foundations.css`, `@wordpress/theme` 4.0.0 `prebuilt/css/design-tokens.css` for `--wpds-*`, Transporter rules in `assets/ran-booster-onboarding.css:455-1270`. Relative-luminance WCAG 2.x ratios computed with a script (scratchpad `contrast.py`). Only light values exist: Booster CSS and the theme prebuilt file define no dark or high-contrast variants and the plugin has no `prefers-color-scheme` rules, so light is the actual rendering today (the only `forced-colors` rule is the shell background). WP core control styles (input border `#8c8f94`, `.description` `#646970`) are taken from WordPress defaults, not this repo, so treat them as approximate. Thresholds: text 4.5:1 normal (below 24px, or below 18.66px bold), 3:1 large text and non-text UI.

### Surfaces

Card `#fff` (`--wpds-color-background-surface-neutral-strong`); inner "panels" (`__upload`, `__review`, `__apply`, `__export-packages`, `__credential-option`, credential actions) use `--ran-booster-surface-subtle` `#f0f0f1`; credential cards inside the panels go back to `#fff`; hover/selected mode uses `#e5f3ff`; unavailable credential cards use `#f0f0f1`.

### Text (normal size, 13-16px)

| Role (selector) | Colour | on `#fff` | on `#f0f0f1` | on `#e5f3ff` |
|---|---|---|---|---|
| Body, titles, labels | `#1d2327` | 15.89 | 13.95 | 14.07 |
| Mode/status descriptions, unavailable cards, disabled-state explanations (`--ran-booster-text-muted`) | `#50575e` | 7.33 | 6.43 | 6.49 |
| WP `.description` help | `#646970` | 5.53 | 4.86 | 4.90 |
| Links | `#12395b` / `#135e96` | 11.92 / 6.84 | 10.46 / 6.01 | 10.55 / 6.06 |
| Status badges (wpds, all intents) | tokens | 13.3-16.7 | | |

All pass AA (4.5:1). The lowest real figure is WP help text on grey panels at 4.86 (13px help, passes narrowly). Disabled/unavailable credential explanation text is 6.43, so essential eligibility explanations are readable. Not used as text anywhere in Transporter (so not failures): `#008a20` status-ok is 3.96 on `#f0f0f1`, `#996800` warning is 4.25 on `#f0f0f1`; flag them for any future use as text on grey (they pass only on white: 4.51 and 4.84).

### Findings

1. No text contrast failure at AA (normal or large) in any measured Transporter text/background pair.
2. Advisory, not a clear fail: the two entry buttons ("Create a Blueprint", "Open a Blueprint") are identified by text, so their `#c3c4c7` borders (1.74:1) are not strictly required by 1.4.11, but they are the only affordance and are weak. The fix in tokens is already present in the codebase: `--ran-booster-strong-divider` `#8c8f94` (3.24:1 on white) or wpds `stroke-interactive-neutral` `#8d8d8d` (3.32:1). I list this as a recommended token-level fix but did not apply it, because it changes the look of an entry control and the owner is deciding the hierarchy.
3. Native controls inside `#f0f0f1` panels (WP input border `#8c8f94` about 2.85:1 on grey) sit just under 3:1 where a text input or checkbox sits directly on a panel. Cause is the grey panel, not the control; removing the grey panel (option below) restores 3.24:1. Verify visually, since this relies on WP core values.
4. The "muddy grey-on-grey" is not a text-contrast problem; it is a separation problem: `#f0f0f1` panels on a `#fff` Card are only 1.14:1 apart, with a `#c3c4c7` hairline (1.53-1.74) on some and none on others, and white credential cards inside the grey panels create a third nesting level (Page grey, Card white, panel grey, row white).
5. Mode-pressed state is signalled by border and tint only; `aria-pressed`/`aria-expanded` are present, but a non-colour visual cue (check mark or heavier border) would be needed to meet 1.4.1 for sighted users who cannot discriminate the tint (the 2px blue border at 5.17:1 against white is arguably already a shape change; owner eyeball).
6. Icons: `dashicons-upload` for "Create a Blueprint" and `dashicons-download` for "Open a Blueprint". The metaphors are inverted/ambiguous (upload is shown for making an export; download for opening an import). Both are `aria-hidden` and the button text names the action, so this is a semantics/clarity issue, not an accessibility failure. 32px grey glyph is the weakest part of the buttons visually.
7. Forced colors: no Transporter-specific `forced-colors` rules; the grey panel fills vanish, and borders become system colours. Dashicon glyphs are font-based and follow `CanvasText`. Unverified visually.

### Hierarchy and icon options (not applied)

Hierarchy:

A. Flatten: keep the white Card as the only container; remove the grey fill from `__upload`, `__review`, `__apply`, `__export-packages`; separate sections with a 1px `--wpds-color-stroke-surface-neutral` divider and the 16px sub-section heading (16/600). Keeps credential cards as the single inset frame.
```
[ Card ]
  Create a Transporter Blueprint            (20/500)
  intro text
  ---------------------------------------- divider
  Packages                                  (16/600)
  [ ] row  [ ] row
  ---------------------------------------- divider
  Credentials
  [credential card] [credential card]
```
Fewest nested frames; fixes finding 3; changes `onboarding.css:571-581`.

B. Keep panels but make them a defined inset: 1px `--ran-booster-border` and `--wpds-border-radius-md`, use `--wpds-color-background-surface-neutral-weak` `#f4f4f4`. Little contrast gain (about 1.1:1), more nesting; not recommended.

C. Two-card split: promote Packages and Credentials to their own sibling Cards (24px card gap, 24/32/24 insets), consistent with the Card conversions elsewhere; heaviest change, best consistency with the #629/#633 direction.

Recommendation: A first (one rule block, no markup), then C only if the owner wants Cards per step.

Entry choices: keep two buttons as before, strengthen the border to `--ran-booster-strong-divider`, add a visible selected cue, and rename icons to a consistent pair from the supported icon set (the dashicon family already loaded; no new library). Candidate: swap the existing `dashicons-upload`/`dashicons-download` pair (names not checked against the loaded dashicons set) so export = out-of-site (arrow leaving), import = into-site (arrow arriving); the owner should choose which metaphor. Alternative: use `@wordpress/icons` already present via `@wordpress/ui`? Unverified, check export availability before choosing.

Entry-button border `--ran-booster-border` to `--ran-booster-strong-divider` (3.24:1). It is unambiguous in ratio terms but is a design call on the entry buttons, so left to the owner.
