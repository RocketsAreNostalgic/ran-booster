# Package update orchestration decision register

## Purpose

This register preserves material package-update approaches that were rejected,
removed, or deferred. It prevents later work from repeatedly rediscovering the
same design and records when changed evidence would justify reconsideration.

This is durable decision history, not a temporary plan or the runtime contract.
It remains in `docs/` when proposals are completed, archived, replaced, or
removed. The current operational sequence remains in
[Package update orchestration](package-update-orchestration.md). Active
proposals may link here, but this register must remain self-contained.

## How to use this register

- Check this register before proposing a new updater, installer, lock, receipt,
  credential lifecycle, public facade, or cross-path abstraction.
- Do not reopen a decision merely because the rejected design is technically
  possible. Name the reconsideration trigger and provide new evidence.
- Re-evaluation changes a row's status only through a reviewed plan or decision
  update. Preserve the earlier rationale and append the new decision.
- “Deferred” means the problem may be real but does not justify the production
  complexity at the recorded scale. “NO-GO” means the approach fails a current
  correctness, compatibility, security, or maintainability boundary.
- Treat production lines and concept count as separate, restricted budgets.
  Deleting tests and documentation does not offset production growth, and
  deletion in one repository does not justify an abstraction in another.
- A positive Core delta or new Core service, DTO, registry, facade, public seam
  or persistent field requires the owner's approval before implementation,
  supported by a current Core-owned invariant, rejected smaller alternatives
  and an exact projected delta.

## 2026-07-31 exact-release Reinstall re-evaluation

The package-settings review identified a real expectation that a
release-managed plugin or theme can reinstall the currently published artifact
for its installed version. This satisfies the demonstrated-demand half of
PU-002's reconsideration trigger, but it does not authorize restoration of the
deleted exact-Reinstall facade, direct executor path, receipt framework or
add-on compatibility shell. Those approaches retain their recorded NO-GO
status.

A smaller candidate requires a test-only feasibility proof before production
planning. A target-bound, nonce-protected request would place an equal-version
offer in memory for one request, then call WordPress's existing single-package
`Plugin_Upgrader` or `Theme_Upgrader` path. WordPress accepts a response entry
without comparing its version, and that path already owns temporary backup,
restoration and completion. The shared updater would still freshly reacquire
and verify the exact release at `upgrader_pre_download`; Core would retain its
existing authority snapshot and updater-lock fence. No offer may survive the
request, and no second installer, branch `DeploymentAttempt`, cached archive,
scheduler, retry engine or generic mutation journal may be introduced.

The feasibility gate must prove plugins and themes, preserved activation,
Manual and Automatic admission, Disabled rejection, exact installed-version
selection when a newer release exists, repository and source-revision races,
mutable-release replacement semantics, assurance rejection, WordPress
restoration and killed-request behavior. If the native path is not equivalent
to the already supported one-target manual Update recovery contract, PU-002
remains closed unless the owner separately approves a durable Core hard stop
and its production-line and concept budget. If it is equivalent, a reviewed P0
plan must record exact Updater, Core and Release Deployments deltas before any
runtime implementation; source-specific UI and handling remain in Release
Deployments wherever Core does not own the invariant.
