# Portability decision register

## Purpose

This durable register preserves material Portability and source-migration
approaches that were rejected, removed, or deliberately deferred. It remains in
`docs/` if an active proposal is completed, archived, replaced, or removed.

Before reopening a decision, name its reconsideration trigger and provide new
evidence. Preserve the earlier rationale when recording a changed decision.

Current Transporter behavior is documented in the
[Transporter Blueprint guide](portability-briefcase.md), and the independent
public extension boundary is documented in
[Portability API 2](portability-api.md).

## Evidence baseline

Reconciled 2026-08-08 against RAN Booster Core
`6ea2644d1f458add4b49828b0e7cd629e19ea593` (`1.0.0-beta.9`), Blueprint V1,
Portability API 2, Provider API 8, and Add-on API 15.

The historical 2026-07-29 review used Core merge `534d484`, exact WP Pusher
3.0.13 source commit `6608ffef25b9f7b6ed376b647aa04c261deab665`, tree
`0a00bfd1cd5a1502c8597d6e3bf2a7843e8659b9`, and preserved source ZIP SHA-256
`4f1533b9b946afdf9d699ea54279ea236b7e25f3d3fc9182bb53cec295a52208`.
At that baseline Core preserved Blueprint V1, Add-on API 9, Provider API 6, and
Logging API 1 while publishing Portability API 1. Later Add-on API revisions
10 through 14 and Provider API revisions 7 through 8 did not merge Transporter
credential transfer into the public Portability API. Portability API 2 remains
a request-local adoption boundary for one already-installed package.

Exact-source inspection also closed the two final Phase 0 feasibility questions:

- WordPress activation sandbox inclusion constructs WP Pusher's container and
  registers hooks, but package mutation remains behind later activation,
  `init`, `admin_init`, and explicit action handlers. The main-file include
  performs no package install, update, unlink, or package-table write.
- All ten scalar package-row columns are available to one prepared conditional
  `DELETE`; `subdirectory` can use an exact `IS NULL` or value predicate. The
  bridge can therefore close the final read/delete race without a new
  transaction, table lock, or source runtime call.

## Shipped behavior and future control boundary

Blueprint V1 currently supports optional encrypted credential transfer. A
credential-bearing archive is password-protected with AES-256; a package-only
archive remains available without credential material. The archive credential
schema contains provider, label, declared kind, configuration, secret, and
package associations. It does not contain a Core profile ID, import UI choice,
`self_destruct`, or `destroy_on`.

Landings A and B implement PT-016 through PT-020: explicit eligible profile
selection, fresh self-destruct rejection, equal declared-kind eligibility, no
permission or expiry assurance, and an explicit request-local import, saved
target, or leave decision for every carried credential. Preview does not
persist transferred material. Apply verifies only the selected source and
reports credential availability separately from the package outcome, without
claiming whether a deterministic imported profile was newly created. Source
profile IDs, target profile IDs, and both export and import choices remain
request-only authority selectors and are not added to `blueprint.json`.
Blueprint V1, Portability API 2, Provider API 8, and Add-on API 15 are
unchanged.

## Implemented corrections

- Blueprint V1 permits 128 packages, but the earlier review view silently
  rendered only 100. The shared 128-package bound now applies without silent
  truncation.
- Successful Apply formerly proved only identifier and Disabled policy. The
  shared application service now requires full package management-tuple
  readback before the public facade can return `targetVerified`.
- Focused characterization covers public upload and Apply handlers, action
  changes, adopt opt-in, capability combinations, and row 127.
