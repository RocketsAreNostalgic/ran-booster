## Branch-evidence fallback reachability follow-up

**Conclusion: cleanup debt, not a demonstrated supported-production defect or a new release blocker.** This follows source/bootstrap tracing, not installed-site testing. The class exposes success-shaped fallbacks outside WordPress, but the maintained production entrypoints do not use that environment.

- Official [WordPress 7.0 `wp-settings.php`](https://github.com/WordPress/WordPress/blob/b16cd68ea199838d8f9daf0ff7e3f35042ba0ad0/wp-settings.php) requires `wp-includes/functions.php` (which requires `option.php`) and calls `require_wp_db()` before active plugin inclusion. `wp-includes/load.php::require_wp_db()` loads `class-wpdb.php` and instantiates `$wpdb` unless a database object was supplied. `SHORTINIT` returns before active plugins load. The tag was resolved to the exact commit in this link; files were read from that tag.
- Core `ran-booster.php` refuses direct calls without `WPINC`, composes services during plugin loading and calls `Booster::init()` inside its `plugins_loaded` callback at priority100. Defining `WPINC` alone is not a supported bootstrap: earlier unguarded WordPress API calls already require the host. `Booster::init()` registers the purger and Dispatcher on `admin_init`; the dashboard route is registered through the admin menu.
- Exact production store consumers are `ProviderSettingsPresenter::record_package_repository_branch_check()` (remote-check observation), `ProviderProfileAdminController` profile/default mutations, `CredentialSelfDestructPurger::purge()` and `PackageRemovalService::unlink()`. Searches found no CLI/standalone production caller of this store. Branch checks run through `WordPressUpdaterLock::run()`; removal acquires that lock before clearing evidence; replacement uses the updater lock as well. That outer lock actually uses `$wpdb` without the success-shaped missing-object fallback. **Current clarification:** this applies only to those outer-locked operations, not every evidence-store consumer. Dashboard `find()` reads are direct; `CredentialSelfDestructPurger::purge()` profile/provider generation bumps and `ProviderProfileAdminController::manage_public_lookup_profile()` provider generation bumps have no outer updater lock and rely on the store's advisory mutation lock. Full WordPress bootstrap, rather than universal outer locking, supports the missing-host reachability conclusion.
- Advisory evidence is not deployment authority. `find()` returns null without readable records; the dashboard accepts cached `verified` only when stored evidence still exists. Actual option-write failure is compared with readback and throws on a changed value; SQL advisory-lock acquisition/release failure returns false and becomes an exception. `ProviderSettingsPresenter` maps recording exceptions to `unable_to_check`. Expired secrets remain withheld independently even if best-effort purger invalidation fails.
- A non-mutating bare-PHP reflection probe against the exact audited Core class confirmed `get_option=false`, `update_option=false`, `wpdb_present=false`, with `write_option`, `acquire_mutation_lock` and `release_mutation_lock` each returning true. No database or filesystem persistence was invoked. This proves the isolated fallback exists; it does not reproduce a supported WordPress request. `tests/Admin/RepositoryBranchCheckEvidenceStoreTest.php` supplies an in-memory store with explicit read/write/lock overrides, while `RemovalBranchCheckEvidenceStore` in `tests/PackageRemovalServiceTest.php` overrides option IO and inherits the missing-database lock accommodation.

**Disposition owned by #160:** prefer explicit test seams and a separately reviewed removal/fail-closed simplification of unsupported missing-host behavior after #124 baseline capture. No urgent bug fix or new production API is warranted by this evidence. A demonstrated supported request reaching a missing option API or unusable `$wpdb` would change this disposition. Arbitrary third-party global replacement, unusual database drop-ins and custom partial-host embedding were not certified safe by this audit.

## PreparedArtifact covariance under the current boundary

`RepositoryReleaseArtifact::handoff_to_core()` returns `RepositoryReleaseArtifactCustody`. PHP permits a concrete implementing return type such as `PreparedArtifact`. Current `ReleaseArtifactCustodian::claim()` validates size/hash evidence and calls `assert_unchanged()` before returning the already Core-owned artifact; otherwise it makes a bounded private Core copy and verifies/discards provider custody. The branch is not a bypass around hash or filesystem validation.

The current installed-provider fixture uses this concrete form. Current GitHub Provider beta.12 uses its own custody implementation. Bitbucket does not supply this GitHub release-artifact path, and Migrator consumes portability/admin interaction rather than this handoff. Therefore the API10 comment should eventually be replaced with the current contract rationale; it does not show that API10 plugins are accepted, nor prove production providers still require the concrete return. This audit deliberately leaves the runtime file unchanged.
